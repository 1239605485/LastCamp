# 末日营地：安卓像素生存游戏开发设计文档

版本：v0.1（逻辑审查稿）  
日期：2026-10-26  
项目名称：末日营地（工作代号，未确定正式名称）  
目标平台：Android，横屏，优先 arm64  
文档用途：需求交接、玩法评审、开发拆分与验收依据。本文不是已完成产品说明，也不代表项目已经编译或实机验证。

## 1. 文档结论与使用规则

项目已有完整主循环：经营长期营地，白天探索建筑搜集物资、武器和人员，黄昏返程准备，夜晚抵抗尸潮，战后恢复并安排下一次行动。

主要问题不是缺少玩法，而是跨系统规则尚未闭合。本稿将死亡、夜归、同伴、物品归属、营地破防和保存规则补成可以讨论和实现的一套方案。

本文使用三种状态：

- **已确认**：用户明确提出或接受，后续开发应保留。
- **建议默认**：本稿为使逻辑完整提出的规则，不应声称用户已批准；可用于估算和原型设计，正式实现前随本文一起评审。
- **后续候选**：不进入第一版，不因文档提及就自动扩大开发范围。

所有数值、版本选择、内容数量和性能目标，除另有说明，均为建议起点，需通过原型和安卓实机调整。

### 2.1 不能误当成已确认的内容

圣诞玩具工厂、永久暴风雪、强制供暖站、随机三选一升级、同伴永久死亡、载具、联机、宠物、全部家具双人抬运，以及写实弹匣管理，均未正式确定。

## 3. 整体逻辑审查与建议修改

| 问题 | 原先讨论的风险 | 本稿建议 |
|---|---|---|
| 像素小人物与等距高清画面混用 | 地图、人物、家具比例无法统一 | 按 Mini DAYZ 式俯视略带立面的方格地图统一，不采用菱形等距坐标作为首版基础 |
| 白天搜集与夜间高强度战斗争夺弹药 | 外出开枪后无力守营地，迫使玩家回避射击 | 普通敌人可用近战处理；守营地有设施支援；弹药来源不只依靠击杀 |
| 允许夜归但营地只在玩家到场后战斗 | 玩家可离开营地跳过防守 | 同一世界时间驱动营地事件，玩家不在也有持续、可追溯的防御结果 |
| 营地远程结算只有随机扣血 | 返回时感觉被系统随意惩罚 | 结算关联明确的敌人、入口、防御物、人员、弹药；保留战斗日志和状态 |
| 玩家死后回营地导致免费传送 | 利用死亡带货、跳过夜晚 | 全部物品留在死亡点；死亡与复活经过时间，期间营地继续处理事件 |
| 可救起与永久死亡规则混淆 | 同伴莫名消失、反复读取刷新状态 | 首版同伴倒地不会因倒计时永久删除；有救援、待救和恢复状态 |
| 家具既能储物又能打包 | 可以复制内容、无限扩大背包容量 | 转移是单一归属变更；家具打包前清空，物品包保留原家具状态 |
| 把家具摆成封闭圈 | 僵尸卡住，玩家也无法通行 | 阻挡物可受击破坏；布置预览检查占用和友方出入，敌人能攻击障碍 |
| 强化、熟练度、装备品质层层叠加 | 战力难以平衡，失去生存取舍 | 首版优先武器基础差异与配件，熟练度只小幅改善操作，不加入随机属性装备体系 |
| 复制 PC 端操作深度 | 背包和弹匣操作挤占移动端战斗 | 简化弹药管理、情境交互、单击转移，保留扩展接口 |
| 内容扩张过快 | 系统都开始做，但完整一天无法玩通 | 先交付一张小地图、一个营地、一轮昼夜和可回收死亡掉落 |

## 4. 产品定位与参考边界

一句话定位：一款以小人物像素表现的单人末日生存游戏，玩家白天进入建筑搜集、招募幸存者并经营营地，夜晚亲自指挥和参与尸潮防守。

| 参考作品 | 借鉴重点 | 本项目的处理 |
|---|---|---|
| Mini DAYZ | 画面尺度、探索感、生存状态、物资取舍、紧凑 UI | 作为视觉和探索操作的主要参考 |
| 僵尸危机圣诞版 | 武器差异、尸群压迫、炮塔、障碍物和范围伤害 | 放入营地夜战，并保证玩家仍需走位和处理突破口 |
| 僵尸毁灭工程 | 建筑搜刮、门窗、家具、声音和生活设施的联系 | 提炼成适合安卓的规则；不复制全部身体部位、车辆维修和繁复制作系统 |

### 4.1 三种结构比较

| 结构 | 优点 | 代价与结论 |
|---|---|---|
| 巨大无缝开放世界 | 流浪感强 | 内容、加载和离屏模拟成本高，不作为首版 |
| 独立探索副本，回家后才触发夜战 | 容易制作 | 与夜间持续赶路和营地持续受袭的要求冲突，不采用 |
| **持久化分区世界＋统一时钟** | 保留探索路线、夜归和长期营地，能控制加载规模 | **本稿推荐方案，尚未由用户确认技术路线**；分区保存、转场和离屏战斗需要专门设计 |

## 5. 核心循环、时间与暂停

### 5.1 一天的循环

1. 清晨查看营地损失、人员状态、库存和来袭情报。
2. 选择目标，领取装备、弹药、食物和医疗用品，安排留守人员。
3. 白天探索建筑，处理敌人、搜刮、救人和搬运。
4. 根据时间、负重、伤势和情报决定返程。
5. 黄昏修理、制作、补给和布置防线；未返回时可继续赶路。
6. 夜晚尸潮来袭，留守人员先应对，玩家可回来支援。
7. 战斗结束后治疗、修复和整理，为第二天生成明确需求。

### 5.2 时钟规则（建议默认）

- 全世界只有一个权威时钟，室内、室外、营地和不同分区共享。
- 原型一昼夜约 30 分钟真实游玩时间：白天约 18 分钟、黄昏约 3 分钟、夜间约 9 分钟；仅是调参起点。
- 每种行动有游戏时间成本，制作、搜刮、救援、换弹不能靠反复开菜单跳过。
- 入屋、切换分区、复活、读档不重置时间和当夜进攻进度。
- 夜间来袭按当日计划触发，不要求等玩家站在营地里。
- 天亮只改变视野、环境和新增来袭规则，已经出现的敌人不会凭空消失。

### 5.3 暂停与移动端离线（建议默认）

- 首版为单人离线。系统暂停、背包、配件和营地管理等完整面板打开时，整个世界暂停，包括远处营地。
- 确认搜刮、救援、修理或制作后回到世界，以行动进度消耗时间；不是在暂停菜单中瞬间完成。
- 同伴简短指令、武器切换等快捷操作不暂停。
- 切入后台、锁屏或来电时自动暂停并保存；退出游戏期间不按现实时间继续攻营地。
- 暂停时不能瞄准移动、发射或完成世界行动进度。背包内部整理可以立即提交，世界容器取物、存物、安装配件及家具转移则生成待执行请求，恢复世界后才耗时并提交；具体见第 6.4 节。

## 6. 地图、建筑和搜刮

### 6.1 地图结构

- 由固定营地、道路连接和多个持久化探索分区组成。
- 首版用手工小地图保证路线与建筑体验，再考虑随机地点和事件。
- 分区转场只切换显示和加载范围，不改变物品归属或尸潮日程。
- 同伴、敌人、掉落、门窗和搬走的家具都保存其状态，离开再回来不刷新为原样。
- 首版只做一层可进入建筑；楼梯、多层建筑、地下室列为后续。

### 6.2 建筑与物资

| 地点 | 主要产出 | 探索作用 |
|---|---|---|
| 民居 | 食物、衣物、背包、家具 | 早期生存、改善营地 |
| 商店 | 食物、水、电池、常用工具 | 补给、照明 |
| 诊所 | 绷带、药品 | 救援与伤后恢复 |
| 警务点 | 少量枪械、弹药、防护用品 | 初期武装 |
| 修理铺 | 零件、工具、燃料 | 工作台、设施维修 |
| 军事点 | 军用装备、兼容配件 | 中后期高风险目标，首版可不做 |

进入建筑后屋顶隐藏，前景墙按遮挡需要淡出；门窗仍有碰撞和状态。不能因隐藏屋顶而自动显示所有房间的敌人。

容器首次生成时按地点物资表确定内容，并持久化。暂不按每日刷新恢复同一个容器的物资，避免清空后反复读取刷物品。长期资源通过新区域、人员工作、制作和后续补给事件获得。

### 6.3 情境交互

- 靠近对象后显示名称、可执行动作和必要工具。
- 搜刮、开门、翻窗、救援和搬运共用情境按钮，但明确显示当前动作；不能因目标微小变化误丢装备。
- 多个对象重叠时，可切换目标或打开附近对象列表。
- 单击转移为主要触屏方式，拖动为可选补充。
- 不可达容器不能隔墙搜刮；每次确认时重新检查距离、可达性和容量。

### 6.4 暂停搜刮与耗时行动的连接规则（建议默认）

- 玩家背包内部整理、查看详情和快捷栏绑定可在暂停中立即完成，不改变世界位置和时间。
- 对世界容器点击取物或存物时，只建立一条待执行转移请求并显示耗时；物品仍属于原容器，不能提前使用或再次预约同一物品。
- 点击“开始搜刮”关闭面板并恢复世界时间，执行一项或一组明确排队的行动。每项完成时重新校验距离、容量、目标及原物品归属，再原子提交；无需为每件物品重新打开面板。
- 玩家移动、受击、目标被破坏或主动取消会中止未完成项。已完成项保留，未完成项仍在原处；不补扣时间、不复制物品。
- 批量取物按顺序执行，容量不足时停止剩余项并提示，不能把装不下的东西自动扔在地上。
- 配件装拆和家具打包采用同样的“暂停中选择，世界中执行，完成时提交”原则。
- 原型可先限制队列只针对一个附近容器，不实现复杂跨房间任务规划。

## 7. 玩家生存与死亡掉落

### 7.1 首版状态（建议默认）

生命、体力、饥饿、口渴、负重，以及流血/负伤等少量状态。寒冷随气候内容增加，暂不默认每张地图都必须管理低温。

饥渴主要影响远行准备、体力恢复与长期补给，速度需保证玩家能完成一次探索。受伤信息应直观提示原因和处理方法。

首版不加入必然永久死亡的丧尸感染机制；感染、复杂疾病和身体分部位损伤放入后续评审，以免与营地复活和同伴可救起冲突。

### 7.2 外出死亡规则

**已确认：所有随身物品掉落。**本稿将以下内容纳入“所有”：主副武器、近战武器、身上衣物和防具、背包、快捷栏物品、消耗品、弹药、携带材料、打包家具，以及装在枪上的全部配件。

**建议默认流程：**

1. 立即中止玩家行动，生成唯一的遗物容器。
2. 将玩家全部物品转入遗物容器；枪械与配件保持装配关系，背包内容不复制也不删除。
3. 玩家在营地恢复控制；这是游戏规则性恢复，不把装备随之带回。
4. 恢复过程建议经过 1 个游戏小时，期间世界事件正常推进；具体时长可调。
5. 地图标记遗物位置。遗物无自动过期倒计时，可在后续探索回收。
6. 再次死亡生成新的遗物容器，不覆盖旧容器。首版不允许敌人或 NPC 自动搬走遗物。
7. 营地仓库不因玩家个人死亡清空；营地被攻击造成的损失另行计算。

同一把枪的实例 ID、弹药量、耐久和配件必须完整保留。背包作为容器的容量不能因遗物容器嵌套而被重复计入玩家容量。

### 7.3 避免恢复死局

- 初始营地提供一次性基础储备，并引导玩家保留备用装备。
- 营地附近应有可用徒手/简陋工具获得的基础材料；不要让重新起步依赖只有枪才能消灭的敌人。
- 不按每次死亡免费发放可出售的枪械或补给，避免刷资源。
- 玩家在营地内死亡后的处理，以及营地整体失败，见第 10.4 节；这是建议，非用户已确认内容。

## 8. 枪械、配件和战斗

### 8.1 战斗操作（建议默认）

左侧摇杆移动，右侧瞄准并开火，提供开关式轻度辅助瞄准；投掷、换弹、切枪、互动使用少量独立按钮。辅助瞄准不能隔墙锁定，近距离交互优先级与战斗分开。

近战用于节省弹药并处理落单敌人，具有距离、攻击间隔和体力成本。枪械用于处理紧急威胁和尸群；其声音产生新的风险。

### 8.2 弹药规则（建议默认）

首版采用“枪内弹药＋背包中同口径散装弹药”。玩家执行换弹时消耗散装弹药补入枪内，不管理多个独立弹匣的剩余子弹。配件中的弹匣是改变容量/换弹等属性的实体配件。

中断换弹不扣除未实际装入的弹药。切枪、死亡、掉枪后不自动装满。写实弹匣可作为后续规则，不与首版并行开发。

### 8.3 配件槽

| 配件槽 | 第一阶段功能 | 约束 |
|---|---|---|
| 枪口 | 消音器、制退器 | 不同枪口规格兼容；消音不是完全无声 |
| 瞄具 | 红点、低倍镜 | 改善瞄准或观察，不揭示遮挡后的敌人 |
| 弹匣 | 扩容、快速弹匣 | 只改变枪械相关属性，不凭空产生弹药 |
| 下挂 | 握把、手电 | 对稳定性、照明等产生不同作用 |

MVP 先实现枪口与弹匣两类，其他槽保留设计位置。兼容性由枪械定义和接口标签共同控制，不靠配件名称字符串猜测。

### 8.4 装配事务与边界

- 安装前检查接口、占用槽、物品所有权和操作条件。
- 首版不堆叠多份同槽配件，不同时生效互斥配件。
- 拆下扩容弹匣时，超出新容量的枪内弹药退回背包；空间不足则阻止操作并解释原因。
- 交换配件时先检查被换下物品的存放空间，成功后一次性提交。
- 装配界面暂停，但确认装配后需要在世界中完成操作；战斗中被打断不产生半装配、双重属性或丢件。
- 耐久和维修属于后续阶段；MVP 不先引入卡壳、独立枪管磨损和全武器品质词条。

## 9. 幸存者、分工与救援

### 9.1 角色定位

已确认可招募、培养、安排工作。建议先做守卫、维修和医疗三个专长方向；后续增加搜集、烹饪等。

人员分配具有机会成本：带维修工外出可以处理设备，留在营地可以抢修防线。MVP 外出最多带 1 名同伴，营地最多 3 名 NPC，数量可调。

### 9.2 状态模型（建议默认）

健康 → 负伤 → 倒地待救 → 被救起且负伤 → 回营地休养 → 恢复。

- 倒地同伴失去战斗与正常移动能力，显示清晰标记。
- 玩家靠近后持续救援，受击、移动、距离不满足时中断；无效目标不消耗医疗物品。
- 原型建议救援耗时约 4 秒，完成后恢复少量生命、保留负伤状态。
- 首版同伴不因倒地计时归零而永久消失，也不采用倒地期间继续扣血直至删除的规则。
- 救起后不能立即以满状态反复参战；需要返回治疗，营地设施和药品缩短恢复。

### 9.3 玩家死亡或离开时的同伴处理

- 玩家死亡不删除同行 NPC，也不复制其装备。
- 尚能行动的同伴尝试沿可达路线撤回营地；离屏期间继续推进其撤退事件。
- 已倒地的同伴保留在原位置并在地图标记，允许后续救援，不随玩家复活自动传送。
- 不加载的分区仍保存待救同伴状态；重新进入不能刷新成健康。
- 同伴装备独立归属于同伴；不计入玩家死亡掉落，但可被指令转移或营地装备管理操作改变。
- 首版暂不加入同伴抢救死亡、俘虏系统和永久死亡。更高难度规则需单独评审。

## 10. 长期营地与夜间守卫

### 10.1 营地分层

外围路障和陷阱 → 战斗设施与工作区 → 核心避难屋。外围失败后可以退守，避免一个缺口直接删除整个存档。

| 设施 | 作用 | 与探索的联系 |
|---|---|---|
| 仓库 | 储存备用物资、材料 | 带回物资形成长期积累 |
| 工作台 | 制作、装配与后续维修 | 需要零件和工具 |
| 床位/医疗角 | 幸存者恢复 | 需要床、药品、医疗人员 |
| 防御物 | 阻挡敌人、争取时间 | 需要木材、家具等 |
| 炮塔 | 支援射击 | 有独立弹药库存，不能无限开火 |
| 瞭望点 | 提供预警 | 人员投入换取更早的信息 |
| 电力设施 | 后续支持照明和设备 | MVP 可先不做完整电网 |

### 10.2 尸潮规则（建议默认）

- 黄昏前或黄昏阶段给出当夜威胁等级、预计方向和时间窗口。
- 主攻营地的尸潮与野外被声音吸引的敌人是不同来源，使用唯一 ID，不能重复生成。
- 前几夜有缓和的教学进攻，之后按日程逐渐增加组合差异；首版每晚至多一场主要进攻，避免反复打断。
- 波次由明确的威胁预算控制，不能只因为玩家仓库多了一把好枪就无限抬高敌人强度。
- 首版特殊怪限定为普通、快速、破坏型三类；后续再做冲锋、自爆等。
- 敌人不能通过门口卡位被永久冻结：找不到可通路径时攻击可破坏障碍，必要时切换目标。

### 10.3 玩家夜归与离屏防御

营地场景没有加载，不等于营地停止。建议采用两种表现、同一份权威状态：

- **玩家在营地**：完整移动、碰撞、射击、敌人 AI 和救援。
- **玩家在外**：按较低频率处理入口、敌人队列、设施阻挡、守卫攻击、弹药消耗、伤害和人员倒地的事件；省略精细路径和动画。

两种模式必须共享实体 ID、生命、弹药、入口归属和事件进度。离屏结算可以简化，但不能只随机扣除百分比物资，也不承诺与完整物理模拟逐帧相同。

返回营地时，先推进尚未结算的时间区间，再加载剩余敌人与现存设施状态；原先已结算的攻击不得再次执行。切出营地后停止该场景的完整战斗推进，由离屏调度接管，不能两套系统同时扣血。

无线电报告具体事件，例如北墙受损、守卫弹药不足、某人倒地。无无线电时仍进行模拟，可仅显示有限的预警信息。

MVP 的离屏战斗只覆盖一个营地、固定入口、简单墙体和三名以内守卫；不同时支持多个据点和大规模自动化生产。

### 10.4 营地破防与失败（建议默认）

- 外围设施被摧毁，留下损坏状态和可回收部分材料。
- 仓库被直接攻击毁坏时，其内容以掉落容器留在原位置，首版不随机删除整批物资。
- 必须区分“外围破防”与“核心完全失守”。核心仍在时，即使损失严重也正常继续，可退守、抢修和救人；不强制回档。
- 核心完全失守标记“本夜防守失败”。**首版不提供在已被占领营地中直接继续的功能**，暂停全世界，保存失败快照并展示结算。
- 结算只提供“读取最近清晨恢复点重试”或“退出到主菜单”。退出后仍保留失败结算入口，不把失败快照误认为可以继续的正常存档；也不静默删除清晨恢复点。
- 清晨重试是明确的时间回退：同时恢复玩家、NPC、地图、遗物、物资、敌人和事件，不能把失败快照中的物品带进重试世界。每次生成的清晨恢复点保持至少一份已验证备份。
- “完全失守后搬到备用据点继续”作为后续候选，需另行设计撤离地图、剩余敌人、人员和库存去向；不能仅停刷敌人就宣称恢复了可玩状态。
- 若玩家在营地死亡但核心未失守，个人按全部掉落处理；当夜剩余进攻继续由留守防御接管，核心安全且恢复时间结束后才能重新控制角色。
- 若个人死亡期间核心失守，则优先进入上述营地失败结算，不能在被占领的位置无保护地循环复活。

该失败方案是为首版避免复活死循环和失守后敌人去向不明而提出的建议，不代表用户已经批准。它不改变“营地外死亡可以掉落后找回”的个人死亡规则；只有核心完全失守才进入本节的重试/退出结算。

## 11. 家具搬运、储物与布防

### 11.1 搬运规则（建议默认）

- 小型家具/物件：清空后打包，作为有重量、有格子占用的物品携带。
- 中型家具：双手搬运，降低移动速度，不能同时使用枪械；可随时放下。
- 大型家具：首版仅拆成材料，手推车、载具和双人抬运列为后续。
- 所有家具可旋转、放置在有效网格；放置前显示占用和碰撞预览。
- 已接受的“家具搬回营地”不等于已经选择搬运细节，本节为建议实现。

### 11.2 物品守恒

家具实例在世界实体、搬运状态、背包物品三者中只能属于一个位置。打包需清空家具内部；过程中不能借打包把完整仓库套进小背包。

放置保留家具实例 ID、耐久、样式及功能。破坏后生成材料或内容掉落一次，原对象删除一次。装饰品不得无限拆放刷材料。

堵门功能来自实际碰撞；僵尸可以攻击家具，队友需要绕行。营地布置时检查至少一条从核心到出口的友方通路，明确提示阻挡位置；敌方入口可以被封堵，但必须有可攻击的阻挡目标。

MVP 用空储物箱/小柜子演示完整“屋内找到→带回→放下→储物/挡路”流程，中型双手搬运在下一阶段补充。

## 12. UI 与安卓交互

### 12.1 视觉原则

参考 Mini DAYZ 的像素语言和简洁程度，独立制作图标、边框和排版。角色像素尺寸小，不意味着文字和触摸目标也必须小。

中文优先可读，避免为了像素字体牺牲汉字辨认。颜色之外配合图标和文字表达饥饿、流血、缺弹及负伤。

### 12.2 界面清单

| 界面 | 必要信息 | 主要操作 |
|---|---|---|
| 主 HUD | 生存状态、当前武器、弹药、时间、天气/夜战警报、同伴状态 | 移动、瞄准、开火、换弹、互动、快捷使用 |
| 背包 | 装备、物品格、重量、容量、物品详情 | 使用、装备、拆分、转移、丢弃 |
| 搜刮 | 玩家背包与当前容器并排 | 单件/整组转移；容量不够时不静默丢物品 |
| 配件 | 枪械、槽位、兼容提示、变化预览 | 安装、拆下、交换 |
| 人员 | 专长、负伤、工作、装备 | 分工、携带外出、治疗 |
| 营地 | 建造项、设施状态、需求、库存 | 放置、旋转、修理、升级 |
| 地图 | 已探索区域、营地、遗物、待救同伴和情报 | 设定目标，不自动传送 |
| 战后 | 消耗、损坏、人员状态、失败原因 | 整理与继续 |

### 12.3 触屏与可访问性

- 横屏布局，适配 16:9 至常见较长屏幕，避开刘海与手势区域。
- 主要触摸热区建议不少于约 48dp；视觉像素图标可小于实际热区。
- 摇杆和按钮支持缩放、透明度、位置调整及锁定，防止操作时误拖动。
- 左手移动与右手瞄准、交互支持多点触摸；第三根手指点击快捷物品不能取消前两根触摸。
- 提供左手模式、文字大小与辅助瞄准设置。
- 物品转移首先保证点按操作，不强制精细拖拽。
- 快捷栏不能把不存在或已经转移的物品继续显示为可用。

## 13. 像素美术与声音规范

### 13.1 建议初始规格

- 世界采用方格图块，建议先以 32×32 像素地块、约 16×24 至 24×32 的小人物为试制范围；最终以安卓截图可读性确定。
- 使用有限像素密度、最近邻采样和整数倍率优先缩放；不混用高清预渲染人物、不同角度建筑和低清 UI。
- 角色朝向和动作先满足行走、持械、攻击、受击、倒地与死亡；四向起步，八向属于后续统一升级。
- 枪械配件在小人身上只表现可读的主要轮廓，在装备详情中显示完整组合。
- 室内外使用同一套地块比例、碰撞高度与家具占格规则。
- 屋顶隐藏、墙体淡出只改变表现，不改变碰撞、声音和敌人的可见性判断。

### 13.2 声音规则

声音分为玩家可听见的音效和 AI 感知事件。枪声、破窗、近战、警报和设施工作分别定义半径及持续时间，不能依据实际扬声器音量决定 AI 是否察觉。

敌人追向最后感知位置，丢失线索后搜索；不永久知道玩家位置。消音器降低噪声而不消除；视觉发现与声音发现可以分别触发。

## 14. 技术路线与模块边界

### 14.1 建议技术路线

Godot 4.x + GDScript，2D 世界，单人离线，Android 横屏，优先 arm64。引擎具体稳定版本在导出验证后锁定；本文不指定未经验证的最新版本。

上述是本稿技术建议，用户尚未确定引擎。现有 Mini DAYZ Godot 复刻和其他仓库仅作为考察对象；没有完成运行、完整性、许可证和安卓性能核验前，不将其认定为可直接使用的项目基础。

相比把旧浏览器游戏套 WebView，独立 2D 工程更便于维护营地持久化、家具交互、同伴和触屏界面；代价是需要自己实现完整玩法。本判断是架构取舍，不是现有源码编译结果。

### 14.2 职责划分

| 模块 | 职责 | 禁止耦合 |
|---|---|---|
| 世界与时间 | 时钟、分区、事件日程 | UI 不可私自改全局时间 |
| 角色 | 玩家/NPC 状态、移动、受伤 | 不把所有枪械逻辑写进角色控制器 |
| 战斗 | 武器、子弹、命中、伤害、配件效果 | 不直接修改仓库文件或存档格式 |
| 物品与容器 | 实例、容量、转移、装备 | 不让 UI 绕过所有权检查 |
| 建筑与家具 | 门窗、占格、打包、碰撞 | 不为每个家具重新实现背包逻辑 |
| 幸存者 | 分工、同伴指令、倒地与恢复 | 远程模拟与现场 AI 不同时推进同一 NPC |
| 营地与来袭 | 防御目标、尸潮日程、离屏结算 | 不采用读入场景就重开一波的逻辑 |
| UI 与输入 | 展示、请求、反馈、触摸映射 | 不作为物品、生命等唯一数据持有者 |
| 保存 | 世界快照、版本、恢复、事务 | 不逐个场景各自写一份互相矛盾的世界状态 |

事件传递只负责通知事实，关键操作通过明确服务提交并返回成功/失败。例如物品转移成功后发出变更通知，不能由两个监听器各自执行一次转移。

## 15. 数据、保存与后台恢复

### 15.1 最小数据模型

| 数据 | 关键字段 |
|---|---|
| 物品定义 | definition_id、类型、重量、格子、堆叠上限、图标、标签 |
| 物品实例 | instance_id、definition_id、数量、状态、唯一 owner/location |
| 武器实例 | 枪内弹药、弹种、已安装配件 instance_id、状态 |
| 容器 | container_id、容量、物品列表、世界位置/归属者 |
| NPC | npc_id、专长、生命、倒地/负伤、任务、装备和位置 |
| 家具 | furniture_id、类型、位置、朝向、耐久、容器引用、搬运状态 |
| 分区 | 区域 ID、访问记录、敌人、容器、遗物、门窗和移除记录 |
| 夜战 | event_id、所属日、阶段、入口、敌人队列、已处理时间和日志 |
| 世界存档 | schema_version、world_id、随机种子/状态、统一时间、玩家和营地状态 |

### 15.2 保存策略

- 分区转换、死亡掉落、遗物回收、家具转移、人员加入、夜战阶段变化等关键节点进行事务性保存。
- 通过临时文件写入、完整性检查与原子替换提交；保留上一份有效备份。
- 玩家背包清空和遗物创建要在同一事务中完成，断电不能两边都存在或都不存在。
- 配件安装、家具打包和容器转移也使用相同的事务原则。
- 日常退出继续最新存档。单独保留最近清晨恢复点，作为明确可选的手动回退功能；不可与“继续游戏”混为一谈。
- 不基于手机现实时间在后台补扣饥饿、消耗弹药或推进尸潮。
- 随机物资已经生成就保存结果，不能因读档重新抽取。

## 16. 第一版范围与阶段交付

### 16.1 MVP：验证完整的一天

| 内容 | 建议数量/边界 |
|---|---|
| 地图 | 一个营地＋一个小型探索分区，距离能在一天内往返 |
| 建筑 | 三座可进入的一层建筑，至少有后门或不同撤离路线 |
| 玩家与 NPC | 一名玩家、最多三名营地 NPC、其中一名可随行 |
| 战斗 | 一种近战武器、手枪和步枪；普通、快速、破坏型敌人 |
| 武器配件 | 消音器和扩容弹匣，完成兼容、装拆和死亡掉落 |
| 物资 | 食物、水、绷带、两种弹药、木材、零件等少量明确类别 |
| 家具 | 一个可打包带回并重新储物/挡路的小型箱柜 |
| 营地防御 | 墙/路障、入口、仓库、简单守卫；炮塔视原型进度进入下一阶段 |
| 时间 | 连续昼夜、可夜归、营地离屏防御与警报 |
| 死亡救援 | 全部掉落、回营恢复、遗物回收、同伴倒地与救起 |
| UI | 主 HUD、背包/搜刮、配件、简化人员、地图、暂停与保存 |

验收目标是“能从出发一路玩到战后，并在下一天看到昨天留下的结果”，不是分别演示几个互不相连的界面。

### 16.2 可持续营地版本：至少连续七天的资源闭环

一天 MVP 只证明系统相连，不应宣传为能长期经营的完整版本。首次供正常多日游玩的版本还必须补齐下列最低来源，并完成至少七天的平衡验证：

| 资源 | 建议最低持续来源 | 防止刷取与成本规则 |
|---|---|---|
| 水 | 营地附近一处可使用的水泵，容器可反复装水 | 取水耗时，携带受重量限制；首版水泵取水可直接饮用，不额外叠加净水系统 |
| 食物 | 地图上有限采集点按世界日程恢复，或指派 NPC 到这些点采集 | 同一采集点共享产出，手动与 NPC 不能重复领取；建议每两天恢复一批，重读不刷新 |
| 弹药 | 有上限的周期补给事件，例如每三天一个有预警的补给点 | 需外出领取且每个 event_id 只能领取一次；数量有上限，不按死亡次数补发 |
| 基础材料 | 有限的周期拾荒点，或人员对相同拾荒点执行任务 | 产出有共享库存和世界日程；首版不加入完整种树/采矿产业链 |
| 无弹药时的防御 | 可重复使用的基础近战武器、可修复路障、降低强度的恢复日 | MVP 不消耗近战武器耐久，避免材料断供后彻底失去行动能力 |

这些是建议默认的最低供给机制，属于 MVP 之后、正式多日版本之前的必要工作。数值应以人口消耗和每夜压力倒推；不能只加入恢复点却不检查七天总供需。定期补给也必须允许提前规划，不能出现连续多日必需弹药无法获得却仍强制同强度尸潮的情况。

### 16.3 后续阶段

1. **体验完善**：修正操作、昼夜节奏、补给经济、路径、离屏模拟偏差和存档问题。
2. **内容扩展**：更多建筑、枪械、配件、家具、炮塔、救援事件和 NPC 专长。
3. **环境与长期成长**：天气、寒冷、供电供水、有限生产、区域通讯任务。
4. **后续评审**：载具、手推车、双人搬运、多层建筑、农业、联机和大型开放世界；未经重新评估不纳入承诺。

## 17. 性能预算与质量要求

- 先指定一台实际安卓设备作为基准，记录机型、系统、内存与分辨率；未指定前不承诺“所有手机流畅”。
- 原型目标：常态争取 60 FPS；压力夜战至少维持可操作的 30 FPS，具体敌人数通过实机测量决定。
- 纹理使用统一图集并按分区加载；避免一次加载所有方向、角色和地图资源。
- 子弹、命中特效和短时掉落表现可复用对象；不可复用正在持久化的物品实例 ID。
- 僵尸寻路分批更新，远处降低频率，障碍改变后局部更新路径；不让每只僵尸每帧重算全图。
- 首版性能评估至少覆盖 30、60、100 个敌人的梯度场景。若最高档不达标，应记录并确定设备可用上限，不能隐瞒或直接认定该数量已支持。
- 内存、温升、加载卡顿与电量消耗需要持续游玩测试，不能只看启动后的瞬时帧率。

## 18. 验收场景与风险验证

| 编号 | 场景 | 通过条件 |
|---|---|---|
| T01 | 搜刮后跨区再返回 | 已取走物品不重生，容器与门窗状态正确 |
| T02 | 天黑时仍在建筑中 | 不强制传送，视野和危险变化，营地事件照常推进 |
| T03 | 尸潮中途返回营地 | 敌人、设施、人员、弹药与离屏日志对应，无重开和双扣 |
| T04 | 反复进出营地 | 同一时间段只推进一次，不刷掉敌人或恢复墙体 |
| T05 | 玩家携带装满物品的背包死亡 | 装备和全部内容留在遗物中，营地仓库不被误清空 |
| T06 | 安装配件后死亡并回收 | 枪械、配件、枪内弹药与身份完整保留 |
| T07 | 连续两次死亡 | 两份遗物均存在，不覆盖、不复制 |
| T08 | 同伴倒地后玩家死亡/跨区 | 同伴待救状态持久化，可再次找到并救起 |
| T09 | 救援被打断 | 不出现半复活、重复消耗或救起死亡目标 |
| T10 | 搬空柜子并放回营地 | 原建筑家具移除，营地只出现一份，状态保留 |
| T11 | 打包有内容的柜子 | 被明确阻止，或要求先清空；不产生容量漏洞 |
| T12 | 拆下扩容弹匣且背包满 | 操作失败并提示，子弹与配件均不丢失 |
| T13 | 用家具封住入口 | 敌人能攻击阻挡物，队友不无限撞墙 |
| T14 | 夜战时打开背包/切后台 | 全世界暂停，恢复后无跳时和双重结算 |
| T15 | 关键转移时强制结束进程 | 恢复最近完整事务，不复制或吞掉物品 |
| T16 | 营地破防且玩家在外/个人死亡 | 按明确失败流程处理，不无限复活或静默删档 |
| T17 | 一天完整流程后保存并继续 | 时间、NPC 工作、物资、防线和下一夜计划连续 |
| T18 | 双摇杆同时使用并点击快捷栏 | 触摸 ID 不串用，移动和瞄准不莫名中断 |
| T19 | 暂停选取批量搜刮后受击中断 | 已完成项归玩家，未完成项在原容器，无复制和无偿瞬移 |
| T20 | 核心失守后清晨重试 | 所有系统一起回退，失败期间获得/掉落物品不能跨快照保留 |
| T21 | 连续七天经营（多日版本） | 水食、弹药、材料来源存在且不重复领取，失败后仍有可行恢复路线 |

验证顺序：数据与事务测试 → 桌面原型玩法检查 → Android 导出 → 基准机完整循环 → 多日压力与恢复测试。不得把“源码看起来正确”标注成“游戏实测通过”。

## 21. 文档复核记录

本稿已进行一次独立开发可执行性复核，并据此补齐三处逻辑：

1. 核心失守后的“继续”与剩余敌人冲突：首版改为明确的清晨重试/退出结算，外围受损仍可正常继续。
2. 暂停背包与耗时搜刮冲突：区分背包内部整理和世界物品转移，增加恢复世界后执行及中断规则。
3. 不刷新容器与长期物资消耗冲突：明确一天 MVP 的边界，并为多日版本增加最低持续水食、弹药和材料来源。

复核属于文档和规则检查，不是代码、游戏运行或安卓实机验证。

## 22. 交给后续开发者的要求

1. 先通读已确认需求和待评审默认，不能把讨论提案当成已批准范围。
2. 先完成纵向闭环，再增加新武器、新敌人和新界面。
3. 时间、物品归属、死亡和离屏战斗先设计清楚，避免后期把状态散落在 UI 与场景脚本里。
4. 各系统按职责分开，修改当前问题时不顺带改变无关系统；失败方案、临时和重复产物在确认引用后清理。
5. 每次交付说明实际完成项、未完成项及验证层级：源码检查、自动测试、编译/导出、桌面运行、安卓实测分别说明。
6. 发生需求变化时更新本文版本和状态标记，不靠聊天记忆悄悄改规则。
7. 原型数值先集中配置，禁止将昼夜、伤害、容量和尸潮强度散布为难以调整的常量。
8. 用户审阅本稿后，再编制具体实现任务和代码方案；本文件交付不表示已经开始游戏实现。
